## D-12　手动模型 `:tools` 声明未进入 binding

### 根因
链路逐段核对：客户端 `draft/set-model-capability` → `catalog/server-capabilities`（`:tools :known`→`true`）→ `connection/server-models`（`:capabilities` 在 `server-model-keys` 内）→ `settings/save-connection` → `snapshot/sanitize-connection`（不丢 `:capabilities`）→ settings 文档 → `session-config/session-config` 的 `model-entry`（`capability-map` 保留 `:capabilities`）→ `sessions/config.clj:268` `model-binding-snapshot` 复制 `:capabilities` 进 `:session/:model-binding` → `system.clj` `current-tools-supported`/`live-tools-supported` 在 live 项无 `:tools` 事实时回落 binding 的 `:capabilities` → gateway `resolve-tools-supported`。**断点**：手动模型创建时 `:capabilities {}`（`draft.cljc:355`），用户若未显式声明 `:tools`，binding 与 live 均无事实，`fallback` 为 nil → `tools? false` → Plan/Reviewer 请求被 gateway 以 `:model-tools-unavailable`/`:MODEL_TOOLS_UNAVAILABLE` 拒绝（`system.clj:803-870`；Owner 侧 `handlers.clj:120-160` `model-tools-problem` 同判定）。即缺口是「手动模型默认无 `:tools` 事实且缺可发现的声明入口在 binding 侧的闭环验证」，不是字段丢失。

### 最小骨架
不改协议形状，只补验证与文案指向：
1. 声明链已通（见上），补一条端到端断言把它钉死。
2. `snapshot/binding-availability`（`snapshot.clj:560-580`）保持只判连接/模型可用性；能力事实由 gateway 单独报告——`MODEL_TOOLS_UNAVAILABLE` 的 `:remedy :select-model` 已有，补 `:capabilities-source` 字段（`:live-model` / `:binding` / `:none`），让 UI 能区分「模型真不支持」与「尚未声明」。
3. `handlers.clj model-tools-problem` 的 `:capabilities (:capabilities binding)` 已透传；确保 `:model-tools-supported` resolver（`system.clj:1825`）对手动模型同样走 `current-tools-supported`（已是同一函数，无需改）。

### 需改文件

## D-13　Plan 账本未清空时会话永不 idle（Nudge 持续注入）

### 根因
`settle-turn-guard`（`guards.clj:2340-2530`）在 turn 结束且无 live/pending 调用时调用 `nudge/decide`。`policy.clj` `central-decision` 对 Plan：ledger 非空 → `:enabled? true :reason :ledger-open`；ledger 空但 milestone 未到 pending → `:milestone-open` 也 enabled。enabled 后 `create-nudge-call`（`guards.clj:2196-2230`）建新 model call，call 终态再触发 settle-turn → 循环。**现有边界只有三种**：legal exit（清空账本/handoff/S1 ask/user-wait）、blocked（permanent/context/`NUDGE_BUDGET_EXHAUSTED`/`TOOL_ADMISSION_REFUSED_LIMIT`）、以及测试/E2E seam `:nudge-suppress`（`system.clj:2060-2070`，仅 `:nudge-enabled? false` 时挂上，属全局关闭而非轮次边界）。没有「本轮到此为止、任务未完、等待外部唤醒」的中间态。snapshot 侧 `unattended?`/`run-status`（`snapshot.clj:855-910`）在 `:turn` 非 nil 或 live nudge call 存在时恒为 running，故 UI 一直显示无人值守。

### 最小骨架
新增「轮次边界」作为第四种 turn 结局，与 legal exit/blocked/suppress 平级：

1. `policy.clj`：observation 增加 `:round-seq`（host 传入，单调递增）；`decide` 在 enabled 判定前检查轮次预算——新增 `:round-budget`（默认如 8，可配置），超限返回 `disabled`，`:reason :round-boundary`，`:exit nil`，`:details {:round-seq n :ledger-keys [...]}`。不新增 transition 类型：`prepare` 对 disabled 返回 nil。
2. `guards.clj settle-turn`：`:else` 分支在 `(:enabled? decision)` 且 `(:reason decision)` 非 boundary 时照旧 `create-nudge-call`；当 decision 为 `:round-boundary` 时走与 `:nudge-suppressed` 同形的提交——`:turn nil`、`history` 记 `{:reason :round-boundary :round-seq n}`、可选 `state/append-outbox {:type :owner/round-boundary ...}` 供 UI/诊断观察。计数存 `[:nudge-rounds key]`（复用 `:nudge-budget` 的 key 形状 `[tenure-id agent-id]`，与 failure budget 分开或合并字段）。
3. `snapshot.clj`：`:turn-active?` 已覆盖 `:turn nil`；`unattended?` 在刚越过边界、无 live call 时应为 false——当前 `has-conversation?`+`actor-active?` 可能仍使 `run-status :running`，需让 `:round-boundary` 最近一条 history 参与判定（或在 state 上记 `:last-round-boundary-at`，snapshot 在其后无新 turn/call 时报 `:run-status :finished`）。
4. 唤醒入口：下一个 `:turn/ended`、用户消息、board/ledger 变化（mission apply-command）自然重新进入 settle-turn 判定——level-triggered，与 suppress 同语义。

### 需改文件
- `src/hc/compose/nudge/policy.clj`：observation/decide 增加 round 维度；`AGENTS.md` §Owner integration 补边界说明。
- `src/hc/compose/owner/guards.clj`：`turn-observation` 传 `:round-seq`；settle-turn 增加 boundary 分支。
- `src/hc/compose/owner/state.clj`：initial-state 加 `:nudge-rounds {}`（若不复用 `:nudge-budget`）。
- `src/hc/server/app/snapshot.clj`：run-status/unattended? 计入 round-boundary。
- `src/hc/client/conversation/surface.cljc:427-445`：确认 `:unattended?`/`:nudge-active?` 投影正确即可，理想无改动。
- `src/hc/server/app/system.clj`：`:config` 增加 `:nudge-round-budget` 透传（可选，默认值在 policy）。

### 测试断言
- 仿 `nudge-suppress-clears-the-turn-as-an-idle-boundary`（`owner_integration_test.clj:1418`）：ledger 非空、连续 N 轮后 `:turn-history` 末条 `:reason :round-boundary`、`:turn nil`、无新 nudge call、`@requests` 计数停止增长；snapshot 投影 `:unattended? false`、`:run-status :finished`。
- level-triggered：再发 `:turn/ended` 仍被判（计数清零或继续按预算）。
- `policy_test.clj`：observation 带 `:round-seq` 超预算 → `decide` 返回 `:enabled? false :reason :round-boundary`。

### 工作量：M　风险：中高
语义敏感：§2.5「账本未清空必须继续」与「轮次边界即停」存在张力，需在 AGENTS.md 明确边界是「宿主预算」而非「任务完成」；误触发会让无人值守任务提前停摆。计数键、重启恢复（state 持久化）、与 `:nudge-budget`（failure-only）不混淆是三个易错点。

## D-19　仅配置 `:main` 时 devops worker unknown model role

### 根因
两层断裂：
1. **Fleet**：`system.clj:4032-4035` `fleet-models` 只在 `:roles :main :model` 与 `:roles :task :model` 同时存在时才构造 `{:main :task}`，否则为 nil → `fleet/start!` 收 `:models nil` → `fleet/actors.clj:524` `start!` 内 `model/new-models`（`mission/model.clj` 要求 `:main`/`:task` 均非空白字符串）抛 `INVALID_MODELS`；即便侥幸通过，`mission/actors.clj:299` `model-for` 对 `:worker`/`:holder` 解析到 `:task`，`(get models :task)` 为 nil → `:model-id nil` 进 `:model/start` → adapter `port.clj:741-750` `resolve-profile` 因 port-state `:roles` 无 `:task` 返回 `:unknown-role`。
2. **devops worker / swarm worker（非 fleet 路径）**：`mission/model.clj:14-30` `role->model-role` 把 `:plan-worker`/`:dedicated-worker`/`:worker`/`:holder` 全部映射 `:task`；adapter `config.clj normalize-roles` 只保留 `:main`/`:task` 角色，`:roles` 仅 `:main` 时 port 的 `:roles` 表无 `:task` → 任何 `:role :task` 请求在 `port.clj:745` 得 `:unknown-role`。`session-config/session_config.clj:76-82` `role-bindings` 会把 settings `:roles` 全量投影进会话 config，但 `sessions/config.clj` 的 roles 集合只认 `:main`/`:task`（`set-role-binding` 拒绝其他角色），且 Owner mission 的 `:models {:main :task}` 由 `state/initial-state` 的 `default-models` 占位或 `:models` 选项注入——`session-owner-factory` 调用 `owner/start-owner!` 处未传 `:models`，实际依赖 mission initial-state；即「仅 :main」在架构上等价于「任务模型未配置」，但报错面是 `:unknown-role` 而非可操作的 `:TASK_MODEL_UNCONFIGURED`。

### 最小骨架
推荐方案 A（显式缺配，不猜默认）：
1. `system.clj:4032`：`fleet-models` 改为由 live session-config 派生——`:main` ← `:roles :main` 绑定的 `[connection model]`（或保持现状取 `:model` 字段），`:task` ← `:roles :task`；缺 `:task` 时仍构造 `{:main m :task nil}` 不行（`new-models` 拒绝），改为在 `fleet/start!` 前置检查：无 `:task` → 不启动 fleet 并写 `:fleet-unavailable` 诊断（code `:TASK_MODEL_UNCONFIGURED`），复用 `model-unavailable-error`/`binding-availability` 的 availability 词汇。
2. `mission/model.clj`：`model-for`/`bind-role` 对缺 `:task` 抛 `ex-info {:code :TASK_MODEL_UNCONFIGURED}`（区别于 `:UNKNOWN_ROLE`）；`new-models` 允许 `:task nil`？——不，保持严格，缺配在更上层拦截。
3. `model_adapter/port.clj:745`：`:unknown-role` 细分——role 为 `:task` 且 port `:roles` 有 `:main` 时返回 `:role-unconfigured`（category `:permanent`，remedy `:configure-task-model`）；真正未知角色仍 `:unknown-role`。`normalize-error`/`failure-class` 相应识别。
4. devops worker 路径（`app/devops.clj` runner → gateway）：`:role :task` 请求遇 `:role-unconfigured` 时，Plan 侧 `devops` 工具结果应返回 `{:status :failed :report "task model not configured"}` 而非裸 adapter 错。

备选方案 B（`:task` 回落 `:main`）：settings 角色投影引入 `:mode :inherit-main` 占位，`session-config`/`fleet-models` 解析为 `:main` 的同一 `[connection model]` 并标 `:inherited? true`——属产品决策，需 spec 确认后再做；本骨架不实现。

### 需改文件

- `src/hc/compose/mission/model.clj`：`model-for`/`bind-role`/`new-models` 错误码细分（或保持，前置拦截已够）。

## D-20　Plan nudge 轮 `:SCOPE_ANNOTATION_MISSING`

### 根因
Scope 注解提取在 `handlers.clj:2073-2079`：只看 `event [:payload :scope]`、`[:arguments :scope]`、`payload [:scope]` 三级。`normalize-scope-annotation`（`handlers.clj:160-166`）只把 annotation map 内 `:kind` 字符串转 keyword。失败路径：`scope-admission-check`（`state.clj:1032` → `admission/check`）对 nil annotation 返回 `:SCOPE_ANNOTATION_MISSING`（`errors.clj:8`）。nudge 轮的快照（`guards.clj:2196-2230` `create-nudge-call`）只追加一条 `{:role :system :text nudge-message}`，**不复述 scope 契约**；模型在长 Plan 对话后极易在下一次 `devops`/`clj-plan` 调用上漏 `:scope`。结构性诱因：`devops-tool-spec`（`devops.clj:126-135`）把 `:scope` 放在 tool `parameters` 内嵌对象且 required，而 `clj-plan`/`clj-review`/`clj-worker`（`prompts.clj:253-307`）同样把 `:scope` 放 `parameters :properties` 且 required `[source intent scope]`——即 scope 是「工具参数的一个字段」，模型若按「tool call 顶层带 :scope」的另一种心智（或 provider schema 剥离/重排）就会缺失。另外 annotation 为字符串（如 `"me-too"`）或 `:scope` 值为字符串时，`normalize-scope-annotation` 不处理整体为字符串的情况，`annotation/parse-annotation` 会以 KIND_INVALID/形状错误失败，与 MISSING 混在同一 refusal 计数里。

### 最小骨架
1. `handlers.clj`：扩展 `normalize-scope-annotation`——annotation 为字符串时尝试解析（`ufss/read-string` 或按 `{:kind (keyword s)}` 包装）；map 内 `:kind` 字符串已处理；保证「有 `:scope` 键但形状错」与「无 `:scope` 键」在 admission 细节上可区分（`(:field admission)`/`(:code admission)` 已有，`record-tool-refusal` 把 `:last-code` 记下，diagnostic message 可按 code 分支）。
2. `guards.clj` `create-nudge-call`：central 与 worker 两支的 system nudge 消息尾部追加一句 scope 提醒（或在 `policy.clj` `worker-message`/`central-message` 尾部加），例如「每个非豁免工具调用必须携带 `:scope {:kind ...}`，与工具 schema 一致」。
3. `handlers.clj` refusal 文案：对 member ∈ `#{devops clj-plan clj-review clj-worker}` 且 code `:SCOPE_ANNOTATION_MISSING` 的 diagnostic，message 明确「`:scope` 是该工具参数内的必填字段（与 schema `required` 一致），不是 tool call 顶层字段」——消除模型对层级的误解。

### 需改文件
- `src/hc/compose/owner/handlers.clj`：`normalize-scope-annotation`、refusal 消息分支（`record-tool-refusal`/diagnostic 组装 ~1640-1690、~2079-2160）。
