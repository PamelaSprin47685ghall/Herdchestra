## 6 E2E 07 `SCOPE_ANNOTATION_MISSING` 定性（scope-diag）

### 复现方式

- 真实 app + 真实 Ollama；在 app 与 Ollama 之间加只读 HTTP 日志代理
  （`/tmp/hc-e2e-harness/scope-diag/proxy.js`），记录 provider 请求与 SSE
  响应；本地搜索 stub 正常返回。
- 同一页面完成模型绑定与“联网搜索 → 本地 stub → 本轮必须搜索”，发送
  `请搜索并回答：ALPHA-ONE 来自哪里？用 [1] 引用。`
- 证据：
  - `scope-diag/provider-tools.json`：provider 收到的工具清单。
  - `scope-diag/provider-system-plan.txt`：provider 收到的 Plan 系统提示。
  - `scope-diag/model-tool-call.json`：模型实际 tool_call。
  - `scope-diag/admission-check.log`：准入函数原文。
  - `scope-diag/ui-receipt.txt`：UI 回执。
  - `scope-diag/requests/003-POST_v1_chat_completions.json`：完整请求。
  - `scope-diag/requests/001-POST_v1_chat_completions.response.txt`：SSE。

### 实际观察

provider 请求同时包含两个顶层工具：

```text
devops   parameters: {"type":"object",
          "properties":{"verbose-intent":{"type":"string"}},
          "required":["verbose-intent"]}          ; 没有 :scope
clj-plan parameters: {... "scope": {..."required":["kind"]}...,
          "required":["source","intent","scope"]} ; 有 :scope
```

系统提示是 **Plan prompt**（`You are Plan...`），其中明确写了：

```text
# Scope
Every non-exempt tool call carries a flat `:scope` map with `:kind`:
`:reset-scope` requires `:new-scope-goal` ... `:keep-last` and `:me-too`
accept no other field; `:remove-last` requires `:replacement` ...
```

模型实际返回：

```json
{"name":"devops",
 "arguments":"{\"verbose-intent\":\"Search the entire repository ...\"}"}
```

即模型选择了**顶层 `devops` 工具**，参数里没有 `:scope`。服务端准入原文：

```clojure
{:ok false,
 :code :SCOPE_ANNOTATION_MISSING,
 :message "tool devops needs a :scope annotation",
 :details {:member "devops"},
 :phase :admission}
```

带合法 scope 的同一成员则通过：

```clojure
{:ok true, :exempt false,
 :annotation {:kind :reset-scope, :goal "search", :budget 2}}
```

模型在收到拒绝后**没有**发起第二轮带 `:scope` 的请求（代理只记录到一次
`chat/completions`；UI 停在“正在生成”）。拒绝回执只有
`:details {:member "devops"}`，**没有** `:expected`/`:allowed`/修正提示；
期望的 scope 形状只在 Plan prompt 与 `clj-plan` schema 里，顶层 devops
的 schema/拒绝回执都没有把它带给模型。

### 为什么会出现顶层 devops

- `hc.server.app.system` 给每个 Owner 传
  `:plan-tools [mission-devops/devops-tool-spec]`（`src/hc/server/app/system.clj:1628`）。
- Owner 的 `request-tools` 在 `role = :plan` 时把 `plan-tools` 直接拼进
  模型工具列表（`src/hc/compose/owner/guards.clj:1701-1705`）。
- `devops-tool-spec` 自身只有 `verbose-intent`，没有 `:scope`
  （`src/hc/compose/mission/devops.clj:102-111`）。
- Plan prompt 告诉模型在 `clj-plan` 程序里调用 `(devops ...)`，但 provider
  同时暴露了一个同名顶层工具；模型按顶层 schema 调用，缺少 scope。
- `central-role` 对所有没有 execution tenure 的新输入返回 `:plan`
  （`src/hc/compose/owner/handlers.clj:89-98`）。当前产品**没有**普通聊天
  路径；“New session”实际就是 Plan tenure。

### 判定

**product-gap（主因），同时 E2E 07 的“普通聊天”前提是 harness 误用。**

- 产品缺口：Plan 的模型可见工具面同时暴露 `clj-plan` 与顶层 `devops`；
  顶层 `devops` schema 不含 `:scope`，与 Plan prompt 的 Scope 规则矛盾。
  模型按 schema 调用后被准入拒绝。这是可复现的工具面/schema 缺口，不是
  模型凭空违反提示。
- 工装误用：E2E 07 把“New session”当成普通聊天；实际 `central-role` 默认
  `:plan`。在 Plan 路径下，正确入口是 `clj-plan`（带 `:scope`），
  `(devops ...)` 只是 clj-plan 程序内的能力，不应作为顶层工具直接调用。
- 不是纯 `model-noncompliance`：模型选择的是被暴露且 schema 匹配的顶层
  `devops`；拒绝后才没有自行补 scope。

### 最小修复点

1. **首选（去掉顶层 devops）**：不要让 `devops-tool-spec` 进入模型可见的
   顶层工具列表。`src/hc/compose/owner/guards.clj:1701-1705` 的
   `request-tools` 在 `:plan` 时只应保留 `clj-plan`（由
   `src/hc/server/app/prompts.clj:317` 的 `decorate-request` 注入）；
   `src/hc/server/app/system.clj:1628` 的 `:plan-tools` 应删除或仅供
   clj-plan 程序内部使用。这样模型只能通过带 scope 的 `clj-plan` 调用
   `(devops ...)`。
2. **若保留顶层 devops**：在
   `src/hc/compose/mission/devops.clj:102-111` 的 `:parameters` 中加入
   `scope`（与 `src/hc/server/app/prompts.clj:227-244` 的 `scope-schema`
   一致），并在 Plan prompt 明确“顶层 devops 也必须带 scope”。但这会
   制造第二个入口，不如方案 1。
3. **若产品需要普通聊天**：`src/hc/compose/owner/handlers.clj:89-98` 的
   `central-role` 需要显式会话模式（Plan / 普通 chat），普通 chat 不应
   注入 `clj-plan`/`devops`。当前没有该模式。

### E2E 07 的正确执行方式

- 若按当前产品：用 Plan tenure 执行，发送 `clj-plan` 调用（source 内
  `(devops ...)`），scope 用 `{:kind :reset-scope :new-scope-goal "..."
  :new-scope-retention-budget N}`；或直接验证 `clj-plan` 的 scope schema。
- 若产品补上普通聊天模式：普通聊天只暴露普通工具，不应出现 `devops`；
  搜索来源/编号/导出/断网重看再按原 E2E 07 断言执行。
- 在修复前，E2E 07 仍应标 **BLOCKED**，阻塞类别是
  `product-gap + harness premise error`，不是搜索供应商失败。

### 1 Extensions 标签页崩溃 — FIXED

根因不是 `materials/view.cljs`（该文件不存在），而是 `src/hc/client/extensions/view.cljc` 的 `select`：

```clojure
(for [[label value] options]
  (el :option {:value (name value) :key (name value)} label))
```

`options` 的 `label` 是 keyword（`:text`/`:url`/`:archive`/`:http`/`:sse`/`:stdio`），React 把 keyword 对象当 child，报 `Objects are not valid as a React child (found: object with keys {ns, name, fqn, ...})`。真实 Chrome dev build 复现 12 次；release 压缩后即 `React error #31 ... {Ea, name, D, de, G, P}`。

修复：`select` 的 option label、`badge`、`button`、`checkbox`、`field` 的 label/hint、`empty-state` 的 title/body 全部经 `text` 字符串化；`skill-card` 的 `:files` 同时兼容 map 与 vector，并用 `text` 渲染 path/size。

证据：`/tmp/hc-e2e-real/extensions-probe.png`；终端 JSON `panel=true`、`errors=[]`、面板文本包含“MCP 服务器 / 导入 MCP 配置 / 技能”。数据目录 `/tmp/hc-e2e-harness/e2e07`（当前无已安装技能，技能列表为空是数据事实）。
