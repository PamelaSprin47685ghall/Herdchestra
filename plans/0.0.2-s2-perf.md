# 0.0.2 S2 设计：性能路径

- 日期：2026-11-07
- 范围：内存峰值治理（全量 ≤ 2 GiB、单 app ≤ 512 MiB）与三项规模基准（1000 会话 / 单会话 2000 活动 / 两万字中英代码混排草稿）。
- 基线：final22 冻结 `c9cbfdf6` + 树 `1e824c83`，3824 tests / 24735 assertions / 0F / 0E / 354 s；父 JVM `-Xmx1g -XX:MaxDirectMemorySize=512m`，历史 VmHWM 1.87–2.28 GiB（final16b 实测 2.28 GB）。E2E app `-J-Xmx768m -J-XX:MaxDirectMemorySize=512m`，进程树实测峰值 2,371 MiB（app≈947 MiB + Chrome≈1.0 GiB + node≈0.5 GiB）。

## 2. 峰值构成分析

全量单 JVM 峰值 ≈ 堆 committed（≤1 GiB）+ Metaspace/CodeCache（~200–300 MiB）+ 直接内存（≤512 MiB）+ 线程栈（默认 1 MiB/线程，Datalevin/Sente/agent 池数十线程）+ native（LMDB mmap 不计 RSS 但 counts VmSize；`lmdb-dirs` 全局池）。实测 1.9–2.28 GiB 与"堆顶满 + native/线程"一致：**瓶颈不是单点泄漏，而是上限叠加**。

子 JVM（restart-smoke 5 个、recovery/disk-smoke 若干）各 512m 堆 + 256m direct，但**串行执行**，峰值取决于父子同刻 RSS 和：父 JVM 常驻 ~1.5 GiB 时子 JVM ~500 MiB → 合计可逼近 2 GiB。final16b 2.28 GB 即此形态。

单 app：`-Xmx768m` 实测 RSS ~947 MiB（堆未必顶满，但 committed+native+线程≈RSS）；目标 ≤512 MiB 需要堆上限降到 ~384–448m 并削减 direct/线程/native 常驻。

## 3. 降到 ≤2 GiB / ≤512 MiB 的可行路径

### 3.1 全量 ≤ 2 GiB（现实，低风险）

1. **分片全量，保留单树 PRE=POST 门禁**：把 358 个命名空间按目录切成 N 片（建议 4 片：`hc.client.*`、`hc.core.*`+`hc.compose.*`、`hc.server.app.*`+`hc.server.*` 非 app、`hc.server.storage*`+重集成），每片独立 JVM `JAVA_TOOL_OPTIONS` 同 caps 跑 `cognitect.test-runner` 的 `:patterns`/`:nses` 过滤；每片前后各算一次 `find src test | xargs sha256sum | sha256sum`，四片 PRE 全部等于 POST 即冻结成立。**单片峰值 ≈ 单 JVM 1.9–2.0 GiB 串行执行，总墙钟 ≈ 354 s × 分片数（若每片独立加载 classpath，预计 380–450 s/片，总 25–30 min）**。这是保住"同树全过"语义的最稳路径。
2. **替代：单 JVM 降 caps**。`-Xmx768m -XX:MaxDirectMemorySize=384m -XX:MaxMetaspaceSize=192m -Xss512k -XX:+UseSerialGC`（或 G1 + `-XX:MaxGCPauseMillis=200`）。风险：重用例子 JVM 另算，父 JVM 768m 堆对 3824 tests 是否够需实测；owner_state 12 MB 字符串 + property 大对象在 768m 下大概率仍过（堆 used 远低于上限时 committed 才是 RSS 大头）。预期峰值 1.4–1.6 GiB。**推荐先试此项**，失败再分片。
3. **重用例隔离**：restart-smoke/recovery/disk-smoke/store-shutdown-stress 四类已用子 JVM 或内部循环；把它们的子 JVM caps 从 512m/256m 降到 `384m/192m`（`hc.test-jvm/child-jvm-opts`），并确认 `-XX:TieredStopAtLevel=1` 已生效（已是）。store-shutdown-stress 20 次起停在父 JVM 内，可考虑拆成独立 ns 分片。
4. **泄漏门禁常开**：`-Dhc.test.assert-no-leaked-stores=true` 加入 test 入口，杜绝 LMDB 池跨 ns 累积。
5. **禁止并行**：全量与 E2E/基准串行；`/tmp/pixi` 已兜底 caps，规则保留"不用裸 clojure"。

### 3.2 单 app ≤ 512 MiB（可行但需削减，列优先级）

1. **JVM 参数**：`app.mjs` 改 `-J-Xmx384m -J-XX:MaxDirectMemorySize=192m -J-XX:MaxMetaspaceSize=160m -J-Xss512k`。768m→384m 堆砍半；direct 512m→192m（Datalevin native 不用 direct，主要是 NIO/Netty 类，Sente 用 Java-WebSocket 标准 NIO）。预期 RSS ≈ 384(committed 堆上限) + ~150 native/metaspace/线程 ≈ **500–560 MiB**，贴线达标；若实测超，堆降到 320m。
2. **线程栈**：`-Xss512k`（默认 1m）；Datalevin/Sente/http-kit 线程数有限（~30–50），省 ~15 MiB。
3. **启动路径减负**（仅当参数不够）：`verify-owner-states!` 每 session 一次 `read-session` 全分区扫描 → 1000 session 时 O(n²) 读，改成一次 `read-view sessions-partition nil` 复用（见 §4.3）；`session-cache` 已有界无需动；`receipt-window` 已有界。
4. **Metaspace**：`MaxMetaspaceSize=160m` 防 class 常驻膨胀；unlimited metaspace 是 RSS 隐形大头。
5. **E2E 进程树**：Chrome V8 已 512m 上限 + `--disable-dev-shm-usage`；app ≤512 MiB 后进程树 ≈ 512 + 1024 + 500(node) ≈ 2.0 GiB，与全量串行跑即可。

### 3.3 不建议做的

- 不把 Datalevin 换内存库：LMDB mmap 的 RSS 主要是 page cache（可回收），换 DB 不解决 JVM 侧上限。
- 不降 `:mapsize-mib`：128 MiB 是虚拟预留不是 RSS，不是瓶颈。
- 不并行分片 JVM：62 GiB 主机允许 2 片并行（每片 ~2 GiB），但为保 PRE=POST 简单性建议串行；若求快可两片并行，总墙钟减半，峰值合计 ~4 GiB 仍在机器能力内（但与"≤2 GiB"字面目标冲突——**该目标应理解为单 JVM/单 app 峰值，分片并行时按进程树分别计**；写进验收口径）。

## 4. 规模基准可执行方案

### 4.1 1000 会话（服务端 + 客户端投影）

- **服务端**：新建 `test/hc/server/storage/session_scale_test.clj`（或 bench 命名空间 `hc.bench`），用 `support/with-temp-store` 开真实 LMDB；循环 `storage/commit-migration!` 写 1000 个 `session/<id>` 分区的 `:owner-state` 文档（每个 ~50–200 KB，含 conversation/calls），再提交 `sessions` 分区索引。**数据生成**：确定性 `doseq`，doc 由 `(apply str (repeat N "…"))` + 结构化 calls/messages 生成，中英代码混排字符串。
- **指标**：`app/system.start!` 对该 store 的启动耗时（含 `recover-all!` + `verify-owner-states!`）；`export-state` 全量导出耗时/分配（复用 `export_benchmark_test` 的 `allocated-bytes`）；`baseline` 投影耗时（`hc.server.app.snapshot/baseline` 对 1000 owners）。
- **断言/阈值**：启动 < 60 s、baseline < 5 s、export < 30 s、进程 VmHWM ≤ 2 GiB（脚本侧 `/proc/<pid>/status` 采样）。门禁化：`-Dhc.bench.scale=true` 默认跳过，全量分片中归入 bench 片。
- **内存上限**：bench JVM `-Xmx1g` 同全量；1000×200KB 文档 = 200 MB 原始数据 + LMDB page cache，不触 1 GiB 堆（doc 走 `:data` codec 反序列化为堆对象，200 MB 数据 ≈ 400–600 MB 堆——**风险点**：`session-view` 全分区 scan 会把所有 doc 同时物化，1000 大 doc 可能顶到 1 GiB 堆上限；对策是分批 commit + 分批读，或把单 doc 降到 ~50 KB 使总量 ~50–100 MB）。

### 4.2 单会话 2000 活动

- **定义**：一个 owner-state 文档含 2000 条 conversation messages + 对应 calls/board 记录（总 doc 目标 ≤ 4 MB，低于 8 MB guard）。
- **脚本**：同 4.1 的 bench ns，单 session 单 commit；测 `commit!`（含 compaction 前后）、`read-session-view`、`conversation-view` 投影、`snapshot/baseline` 中该 session 的 conversation/history/summary 缓存命中耗时。
- **断言**：commit p95 < 2 s；读视图 < 500 ms；`pr-str` doc < 8 MB；VmHWM ≤ 2 GiB。

### 4.3 两万字中英代码混排草稿

- **已有资产**：`test/hc/client/workbench/scale_bench.clj`（`:ui/draft` 20000 字 `中a` 重复，纯投影测量）、`scale_dom_test.cljs`（jsdom 挂载）、`test/js/scale_draft_probe.cjs`（真 Chrome CDP：insertText/selection/undo/localStorage 持久化/reload 恢复，已实现）。
- **补齐**：把 `scale_draft_probe.cjs` 的文本从 `中a`×10000 换成中英代码混排生成器（`中文 + English + ```clojure…``` + 表格`，确定性 seed），增加：draft debounce 写 localStorage 后 reload 恢复断言、2000 次 input 事件后的 UI 帧耗时、`hc.workbench.v1` localStorage 体积上限（建议 < 1 MB，超出说明 draft 未裁剪）。
- **服务端侧**：draft 持久化若走 session doc，20000 字 ≈ 60 KB UTF-8，远低于 8 MB guard，无额外风险；若走 `materials`/`commands` 链路，复用 §4.2 的单 session bench 覆盖。
- **断言/阈值**：insert < 100 ms、selection < 16 ms、undo < 100 ms、reload 恢复值逐字符相等、JSHeapUsedSize < 200 MB、page `Performance` 指标 Nodes/LayoutCount 增量 < 10%。
- **入口**：`scripts/bench-scale.sh` 串行跑三项：`clojure -M:dev -m hc.bench.session-scale`（或 test ns）→ `verify_workbench_scale_dom.sh` → `scale_draft_probe.cjs --url <e2e app>`；每步前后记 VmHWM，超阈值 exit 1。

### 4.4 基准纳入门禁的位置

- 全量分片中单独 `hc-bench` 片（`-Dhc.bench.scale=true`），PRE=POST 同规则；
- E2E 回归中 `scale_draft_probe` 作为 `@scale` tag 的 playwright 项，默认不进 `pnpm e2e:core`，由发布门禁手动/定时跑；
- 指标落 `plans/evidence/scale-<date>.json`，格式对齐现有 e2e evidence。

## 5. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 父 JVM 768m 堆不够 3824 tests（owner_state 12 MB 字符串、property 大对象、Datalevin page cache 反序列化） | 中 | 先实测 `JAVA_TOOL_OPTIONS=-Xmx768m -XX:MaxDirectMemorySize=384m` 跑全量；OOM 则退回分片方案（每片仍 1g caps，总峰值不变但单 JVM 峰值 ≤2 GiB 达标——**注意：若验收口径是"单 JVM 峰值"，分片+1g caps 已满足，无需降堆**） |
| `session-view`/`list-open-obligations` 全前缀扫描在 1000 session 下 O(n) 每读、启动 O(n²) | 中 | §4.1 bench 会实测；若超时，优化点是 `verify-owner-states!` 改单次全分区读 + `read-session` 增加 `:fields` 投影（只取 `:session` record 不取 messages/board） |
| 单 app 384m 堆 + 192m direct 贴 512 MiB 线 | 中 | 实测后微调；`MaxMetaspaceSize` 与 `-Xss` 是确定性收益 |
| 分片改变测试顺序/共享状态假设 | 低-中 | 现有测试已各自 `with-temp-store`/临时目录，泄漏检测只在末尾；分片需在每片末尾跑 `report-leaked-stores!`；`hc.test-runner/test` 已支持 `:patterns` |
| E2E app 降堆后 restart/restore 场景 OOM | 中 | app-check（14 s）与 E2E 先跑 384m；`restore-supervisor`/`backup` 路径内存峰值最高，重点观察 |
| Chrome/E2E 进程树仍 ~2 GiB | 低 | 与全量串行执行，峰值口径按进程树计仍 ≤2 GiB；若要求更严，Chrome `--js-flags=--max-old-space-size=384` 再压 |
| 基准数据生成本身吃内存 | 低 | 生成器用 lazy seq + 分批 commit；200 MB doc 数据控制总堆 < 600 MB |

## 6. 结论

- **全量 ≤ 2 GiB：现实**。最稳是分片（每片 1g/512m caps，单 JVM 峰值 ≤ ~2 GiB，PRE=POST 四片一致）；激进是单 JVM 降到 768m/384m，需一次实测验证。当前 2.28 GB 峰值主要来自"堆顶 + 子 JVM 同刻"，分片天然消除同刻叠加。
- **单 app ≤ 512 MiB：现实但贴线**。`Xmx384m + direct 192m + metaspace 160m + Xss512k` 预期 RSS 500–560 MiB；若实测超标，堆降 320m 或补启动路径读优化。
- 三项基准：1000 会话/2000 活动走新 bench ns（真实 LMDB + system.start），两万字草稿复用并强化已有 `scale_draft_probe.cjs` + `scale_bench.clj`/`scale_dom_test.cljs`。
