## 1 S1 需求分析

### 1.1 决策框架（Howard）

**要做的决策**：0.0.4 该修什么，才能让「最小可运行」从「这台机器此刻能跑」变成「任何机器按文档跑、结果可判定」。

| 要素 | 内容 |
|---|---|
| 目标 | 新机器（无缓存、无 `.pixi`）按文档一次走通；任一检查的结论可由脚本判定而非人读日志；台账不含过期条目 |
| 备选 | A. 只补可移植性；B. 只补台账；C. 两者都补并加一条冷启动验证；D. 全部重做 |
| 信息价值 | 「0.0.3 在干净机器上能否构建」目前**无证据**——本机 `.pixi` 与 `node_modules` 都是预热的。这一条信息价值最高 |
| 价值取舍 | 可移植性 > 台账准确性 > 新功能。新功能在最小可运行成立前一律不做 |

### 1.2 根因诊断（Dalio）

三个缺口不是并列的，它们有共同根因：**验证只在开发者的机器上发生过**。

| 症状 | 根因 | 证据 |
|---|---|---|
| `release-gate.sh` 用 `stat -c`/`sha256sum`/`date -Is` | 作者在 Linux 上写的，从未在 macOS 上跑 | 本机 `stat -c` 报错 |
| 26 个 `verify_*.sh` 裸调 `clojure` | 同上，假设 `PATH` 已由 Pixi 激活 | 裸 PATH 下退出 127 |
| `e2e-17.spec.mjs` 裸调 `clojure` | 同上 | `spawnSync clojure ENOENT` |
| `live-model-entry` 用 map 查找 vector 文档 | 单测只喂 id-keyed map，从未喂真实 settings 形状 | 声明工具能力后 Plan 拒绝发送 |
| `DEBT.md` 含过期条目 | 台账只在发布时批量清理，缺「修完即删」的纪律 | D-12 描述的根因是错的 |
| `RUNNING.md` 仍写 `:version "0.0.1"` | 版本升级时只改了代码没改文档 | 条件 3 与条件 8 |

**关键判断**：这六条里五条是**同一件事的不同投影**——验证假设了 Linux + 已激活环境。所以修法也应该是同一个：把「环境假设」显式化。

## 2 S2 实施骨架

S1 已把判定标准定为「22/22 E2E + 全量 JVM 0 失败」。S2 要回答的是：**用什么结构让这个判定可重复、可移植、可解释**。

### 2.1 判定的三段结构

判定不是一条命令，是三个正交的层次。任何一层缺证据，结论就不成立。

| 层 | 关心什么 | 载体 | 失败表现 |
|---|---|---|---|
| L1 逻辑层 | 状态转换、责任集合、文件提交合同 | 全量 JVM（4500 tests / 32971 assertions） | 断言失败，有最短反例 |
| L2 界面层 | 真实浏览器、真实流式、真实并发点击 | 22 条 E2E（Playwright + 真 JVM + 真 Chrome） | 截图 + `*-result.json` + trace |
| L3 可移植层 | 换一台机器能不能跑 | `verify:js`（26 脚本）+ `release-gate.sh` | 脚本退出码 |

三层不能互相替代。L1 全绿不证明按钮点得动；L2 全绿不证明别人能跑；L3 全绿不证明行为正确。

### 2.2 环境前置自检

E2E 的失败有相当比例不是产品缺陷，而是环境假定。S2 要求这些假定**先被检查、再被使用**，而不是在测试中途以超时或 `ENOENT` 的形式爆发。

| 假定 | 检查方式 | 不满足时的行为 |
|---|---|---|
| `clojure` 可达 | 优先 `./.pixi/envs/default/bin/clojure`，回退 `PATH` | 报「缺少 Clojure 运行环境」并给出 pixi 安装提示 |
| `.pixi` 存在且架构匹配 | 读 `pixi.toml` 与 env 目录 | macOS ARM 走 `osx-64`（Rosetta），HACK.md §4.2 已记录，不是故障 |
| `node_modules` 完整 | `npx playwright --version` | 报 `npm ci` |
| Playwright 浏览器 | `CHROME_PATH` 指向真实 Chrome | 报「未找到浏览器」 |
| `TMPDIR` 在真实磁盘 | `/tmp` 是 tmpfs 时写满导致假断线 | 固定 `TMPDIR=/var/tmp/hc-e2e`（HACK.md §17.24） |
| Pillow（图像断言用） | `/private/tmp/hc-e2e-venv/bin/python -c "import PIL"` | 报可读原因并以退出码 2 结束（`e2e-06` 已实现） |
| 字体（图像断言用） | 7 条跨平台候选路径 | 同上 |

### 2.3 证据契约

每条 E2E 必须留下能被第三方复核的产物，而不是只有「通过」两个字。

| 产物 | 位置 | 内容 |
|---|---|---|
| 截图 | `plans/evidence/e2e-NN/NN-*.png` | 每个关键步骤一张，文件名带序号 |
| 结构化结果 | `plans/evidence/e2e-NN/e2e-NN-result.json` | `checks`（逐项 pass + detail）、`mockFinal`（请求日志）、`clientBundle`（sha256 前 16 位）、`sourceTreeSha256` |
| trace | `plans/evidence/e2e-auto/playwright-artifacts/**` | 失败时保留；成功时不写 |

`checks` 的 `detail` 必须包含**观察到的实际值**，不能只写 `true`。例如 `temp-write-refused` 的 detail 是 `rows=0 errors=["临时会话不读也不写长期记忆。"]`——它同时证明了「没有写入」与「给出了正确理由」。

### 2.4 缺陷归因的两条判据

E2E 失败时，必须先归类，再动手。归错类的代价是修错地方。

**判据一：失败点是否随修改移动。**

- 移动（E2E 10/11/19）→ 每一层都在剥出下一层，说明是多个叠加缺陷，继续逐层剥。
- 不动（E2E 16 的时区、E2E 21 的费用口径）→ 单一缺陷或测试假设错误，直接定位。

**判据二：产品态与测试态是否可分离。**

若把同一场景换成手工操作仍然失败，是产品缺陷；若只在测试的时序下失败，先怀疑测试假设。

反例记录：E2E 11 的 `turn did not settle` 一开始被当成产品问题，实际是 `waitMockQuiet`（mock 静默）被当作 UI 空闲。产品侧确实还有 D-44 的回执竞态，但那条不是本次失败的原因。**「有缺陷」不等于「这个缺陷是本次失败的原因」。**

### 2.5 并行与串行的边界

| 操作 | 可否并行 | 理由 |
|---|---|---|
| 全量 JVM | 可与其他 spec 的阅读并行 | 独立进程，独立数据目录 |
| `verify:js` | 可 | 独立进程 |
| Playwright E2E | **禁止并行** | 共用 `playwright-artifacts` 目录；两个进程互删 trace，产生假 `ENOENT` |
| E2E 内的多个 spec | 串行（`--workers=1`） | 共享端口与 mock，串行才有确定时序 |

需要并行时唯一的安全形式是 `HC_PW_SHARD=<name>` 隔离 `outputDir`，且各 shard 用不同端口。

### 2.6 收尾与清理

- 每轮 E2E 结束必须确认没有残留 JVM：`pkill -f "hc-e2e"`，否则下一轮端口冲突。
- `plans/evidence/e2e-auto/` 是临时产物目录，不提交；`plans/evidence/e2e-NN/` 是可复核证据，随版本提交。
- 交付实例时用独立数据目录（`/tmp/hc-x/data`），测完清理，不污染开发数据。
