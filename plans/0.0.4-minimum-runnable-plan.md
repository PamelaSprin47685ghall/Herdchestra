## 0 为什么是这一版

上一轮（0.0.2 → 0.0.3）已经交付了 22/22 E2E 与完整的发布台账。本机实测基线健康：

| 检查 | 结果 |
|---|---|
| `--help` | `Herdchestra 0.0.3 server` |
| `--check` | `:store {:open? true}`、`:gateway`、`:retention-gc` 齐全 |
| `npm run release` | 退出 0，`undeclared Var` 0 次，`main.js` 3,150,930 B |
| `swarm-stm-test` | 50 tests / 259 assertions，0F/0E |
| `history-test` + `model-gateway-test` + `system-test` | 62 tests / 396 assertions，0F/0E |
| E2E 01（first journey + OAuth） | 两条路径全过（32.2s / 46.1s） |

所以「让它能跑起来」这件事**已经成立**。真正的缺口是三个层面的**可重复性**：换一台机器能不能跑、换一个人能不能判断是否通过、发布台账能不能被人读懂。

## 1 S1 需求分析

### 1.1 决策框架（Howard）

**要做的决策**：0.0.4 该修什么，才能让「最小可运行」从「这台机器此刻能跑」变成「任何机器按文档跑、结果可判定」。

| 要素 | 内容 |
|---|---|
| 目标 | 新机器（无缓存、无 `.pixi`）按文档一次走通；任一检查的结论可由脚本判定而非人读日志；台账不含过期条目 |
| 备选 | A. 只补可移植性；B. 只补台账；C. 两者都补并加一条冷启动验证；D. 全部重做 |
| 信息价值 | 「0.0.3 在干净机器上能否构建」目前**无证据**——本机 `.pixi` 与 `node_modules` 都是预热的。这一条信息价值最高 |
| 价值取舍 | 可移植性 > 台账准确性 > 新功能。新功能在最小可运行成立前一律不做 |

### 1.2 根因诊断（Dalio）

三个缺口不是并列的，它们有共同根因：**验证只在开发者的机器上发生过**。

| 症状 | 根因 | 证据 |
|---|---|---|
| `release-gate.sh` 用 `stat -c`/`sha256sum`/`date -Is` | 作者在 Linux 上写的，从未在 macOS 上跑 | 本机 `stat -c` 报错 |
| 26 个 `verify_*.sh` 裸调 `clojure` | 同上，假设 `PATH` 已由 Pixi 激活 | 裸 PATH 下退出 127 |
| `e2e-17.spec.mjs` 裸调 `clojure` | 同上 | `spawnSync clojure ENOENT` |
| `live-model-entry` 用 map 查找 vector 文档 | 单测只喂 id-keyed map，从未喂真实 settings 形状 | 声明工具能力后 Plan 拒绝发送 |
| `DEBT.md` 含过期条目 | 台账只在发布时批量清理，缺「修完即删」的纪律 | D-12 描述的根因是错的 |
| `RUNNING.md` 仍写 `:version "0.0.1"` | 版本升级时只改了代码没改文档 | 条件 3 与条件 8 |

**关键判断**：这六条里五条是**同一件事的不同投影**——验证假设了 Linux + 已激活环境。所以修法也应该是同一个：把「环境假设」显式化。

### 1.3 单向门与双向门（Bezos）

| 项 | 门型 | 处理 |
|---|---|---|
| 修 `stat -c`/`flock`/`/proc` 为跨平台 | 双向门 | 直接做 |
| 补 `verify_all.sh` 聚合入口 | 双向门 | 直接做 |
| 修 `live-model-entry` 的 vector 查找 | 双向门 | 直接做 |
| 删孤儿依赖 `@cljs-oss/module-deps` | **单向门**（改 lockfile，影响构建复现） | 先跑 `npm ci` 验证再定 |
| 重写 `DEBT.md` | 半单向（丢失历史） | 只删已证实修完的，保留其余原样 |
| 改 `RUNNING.md` 的发布条件 | 双向门 | 直接做 |

### 1.4 需求清单（工作反推）

从「一个新人拿这台机器之外的环境」反推，他需要：

1. **一条命令装好环境**——`pixi install --locked`。现状：未验证冷启动。
2. **一条命令构建**——`pixi run client-release`。现状：验证过，但依赖 `node_modules`。
3. **一条命令跑全部检查**——现状：JVM 测试有 `pixi run test`；前端有 26 个散装脚本但无聚合入口。
4. **每条检查输出可判定的结论**——现状：`release-gate.sh` 在 macOS 上直接崩，判定不可得。
5. **台账只说真话**——现状：`DEBT.md` 有错条目。
6. **发布文档版本一致**——现状：`RUNNING.md` 混着 0.0.1。

这六条就是 S1 的完备需求。**没有第七条**——任何「顺便加个功能」都不属于最小可运行。

### 1.5 已确认的取舍

- **不追 22/22 E2E 在本机全绿**。E2E 需要真实浏览器与 10+ 分钟，逐条复跑的成本高于收益。选取 01（核心旅程）与 17（最复杂的备份恢复）作为抽样代表，其余沿用 0.0.3 的证据并标明「非本机复跑」。
- **不改 `src/` 的行为语义**。`live-model-entry` 的 vector 查找是修 bug（让已有声明能生效），不是改行为。
- **不加新依赖**。

### 1.6 S1 完成判据

任一条不成立则 S1 未完成：

- [ ] 六条需求每条都有对应的验证命令
- [ ] 「最小可运行」有明确的、可脚本判定的定义
- [ ] 每条修复都能说清「修前会怎样失败」

### 1.7 需要操作员确认的一点

「最小可运行」的边界在哪里——是**能构建 + 能启动 + 能发一条消息**，还是**还要包含备份恢复、定时任务、浏览器接管**？

我的建议是前者，理由：后者已有 E2E 覆盖，而「能发一条消息」是新用户遇到的第一个真实门槛。若认可，S2 按这个边界展开。
